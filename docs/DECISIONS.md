# Decision log

Short entries: what was decided, why, consequences. Add a new entry to
change a decision; do not edit the old one beyond marking it superseded.

| ID | Date | Decision | Why | Consequences |
|---|---|---|---|---|
| D-001 | 2026-11-04 | Streamlit for the UI, with a UI-free core package | Accepted in the target environment; Streamlit, Plotly, pandas and duckdb are what a weaker implementing LLM gets right most reliably; `st.dataframe` covers most tabular screens | Streamlit reruns the page on every interaction, so state is kept small and heavy work cached or run outside the page. The one condition to switch: interactive plotting of millions of raw points, then Panel + HoloViews/Datashader with the core unchanged |
| D-002 | 2026-11-04 | Two packages in one uv workspace: `duckfleet-core`, `duckfleet-ui` | Owner asked for the split and for uv; keeps the boundary enforceable by dependency lists | Core cannot import UI libraries; CI installs with `uv sync --all-packages` |
| D-003 | 2026-11-04 | Per-file JSON profiles are the source of truth; the catalog is a DuckDB file rebuilt from them after every scan | Incremental rescans become trivial (reuse when size and mtime match); the catalog can be queried in-tool; no incremental SQL to get wrong | Catalog build is a full rebuild; fine for hundreds of files. JSON files double as a debugging aid |
| D-004 | 2026-11-04 | The UI runs the scan as a subprocess and parses JSON-lines progress; v0.1 blocks behind a progress bar | DuckDB allows one writer or many readers on a file, never both, so the UI cannot read a catalog mid-build; a subprocess also sidesteps spawn-under-Streamlit problems on Windows; owner accepted blocking for the first scan | Non-blocking UI and scan cancel are open options (F-SCAN-14, F-SCAN-15) |
| D-005 | 2026-11-04 | Process pool with `spawn` context on both OSes, `max(1, cpu_count - 2)` workers, DuckDB `threads=1` and a memory cap per worker | Owner asked for all-but-two cores; spawn is the only context that behaves the same on Windows and Linux; one DuckDB thread per worker avoids oversubscription | Workers pay an import cost at start (about a second); acceptable for hundreds of files |
| D-006 | 2026-11-04 | Read-only everywhere; extension autoload off | Removes a class of risk, simplifies locking, no network access from workers | Encrypted files and anything needing an extension are open options |
| D-007 | 2026-11-04 | Strict (names + types) and loose (names only) fingerprints; column order ignored; views excluded by default | Matches the owner's default answer to "what is the same structure"; order rarely carries meaning | Type aliases are not normalised in v0.1 (TUNING type-normalization) |
| D-008 | 2026-11-04 | Run/experiment identity from path tokens, with a documented tuning convention | Owner: a convention exists but is unknown at this stage | `docs/TUNING.md` and `# TUNING(...)` markers; identity query is an open option |
| D-009 | 2026-11-04 | Cache under the user cache directory (platformdirs), never inside the scanned folder | Owner approved; keeps data folders untouched | Cache location printable with `duckfleet paths` |
| D-010 | 2026-11-04 | Pydantic v2 for serialised models; platformdirs and psutil as small helpers | Mainstream packages; pydantic removes hand-written JSON round-trip code | Three extra core dependencies, all widely available |
| D-011 | 2026-11-04 | Discovery does its own header-magic check and rejects anything without it | Verified: DuckDB 1.5.6 opens files with an SQLite header without error, even with autoload off | SQLite files never reach a worker; SQLite as a fleet member is an open option |
| D-012 | 2026-11-04 | Implementer: Sonnet 5.5 from the detailed plan; Opus-class review at each version's acceptance checklist | Plan pins contracts, verified facts and tests; review catches drift | Each version gets its own `docs/PLAN_vX.md` before implementation |
| D-013 | 2026-11-04 | Windows and Linux are equal targets; CI matrix on both | Owner's answer to the environment question | No POSIX-only modules; tests spawn helper processes with `sys.executable` |
| D-014 | 2026-11-04 | No LICENSE file yet | Owner has not chosen one; a public repository without a license is all rights reserved | Open item for the owner |
| D-015 | 2026-11-04 | Cache directory is `platformdirs.user_cache_dir("duckfleet", appauthor=False)` | Without `appauthor=False` platformdirs doubles the folder on Windows (`...\duckfleet\duckfleet\Cache`) | Windows: `%LOCALAPPDATA%\duckfleet\Cache`; `duckfleet paths` prints the real location |
| D-016 | 2026-11-04 | The catalog is filled by binding one Python list per column and unnesting it (`INSERT ... SELECT unnest(?::T[]), ...`) instead of `executemany` | Plan Section 3.4 rule 4 says `executemany`; measured on 120k column rows (400 files x 10 tables x 30 columns): `executemany` extrapolates to about 56 s, multi-row `VALUES` 7 s, unnest 1.1 s. Still plain Python lists, no pandas | Same result, a scan of hundreds of files does not stall in the catalog step |
| D-017 | 2026-11-04 | A file whose header cannot be read because a writer holds it stays a discovery candidate and is reported `locked` (Windows: `PermissionError` on read counts as locked) | DuckDB opens a file exclusively while a read-write connection exists; on Windows even `open().read()` fails, so rejecting it as `unreadable` would hide the most useful health fact, and Linux would behave differently | `discovery.looks_locked`; LIMITS 11. An ACL problem on Windows is also called `locked`; the message keeps the OS text |
| D-018 | 2026-11-04 | Outcomes of the plan's (TBC) items (Section 10) | 1: the Linux lock message is matched by the existing substrings, the lock test passes on ubuntu-latest CI. 2: `incompatible_version` and `encrypted` stay message-only, no fixture. 3: `st.navigation` is not run under AppTest, the page function is. 4: no `os.replace` problem on Windows, readers never keep a handle (tested). 5: the UI works with pandas 2.2.3 and 3.1.1 | Nothing to change in the code; the open parts are listed in `CHANGELOG.md` 0.1.0. Item 2 is superseded by the v0.1 review: an `encrypted` fixture is producible (R-11) |
| D-019 | 2026-11-04 | The v0.1 review (`docs/REVIEW_v0.1.md`) accepts v0.1.0 and its fixes ship as 0.1.1, Phase 0 of `docs/PLAN_v0.2.md` | Three findings can hit real fleets (catalog overflow on a garbage header, `infinity` time windows, invalid tag regex); fixing them first keeps v0.2 on a sound base | One extra commit before v0.2 work; demo fleet grows by two files (high-bit header, encrypted) |
| D-020 | 2026-11-04 | Per-column summaries (`SUMMARIZE`) are cached as JSON sidecars next to the profiles, not in the catalog | The catalog is single-writer and rebuilt by scans only (D-003, D-004); the UI process must never write it | `<root_dir>/summaries/<file_key>/<table_key>.json`, valid while size, mtime, schema version and DuckDB version match; folding summaries into the catalog is an open option |
| D-021 | 2026-11-04 | SQL page and all in-process opens of a scanned file use one connection config: read-only, extension autoload off, `enable_external_access=false`, `lock_configuration=true`, fixed threads and memory limit | Verified: the locked read-only connection refuses writes, file access, extension loading and `SET`; a second connection to the same file in one process must use an identical config or DuckDB refuses it | The query page cannot be used to read or write files or load extensions; `CREATE TEMP TABLE` remains possible (in memory); threads and memory are resolved once per process, never per page |
| D-022 | 2026-11-04 | `pytz` becomes a dependency of `duckfleet-core`; `pyarrow` an optional extra `export` | The Python client cannot fetch `TIMESTAMP WITH TIME ZONE` rows without pytz (verified); Arrow export needs pyarrow, which the UI already has | Both mainstream; the CLI `sql --format csv` says clearly when pyarrow is missing |
| D-023 | 2026-11-04 | Downloads are built in memory through Arrow and capped at 1,000,000 rows (L-09) | No file writes from the UI process, no `COPY TO` (blocked by D-021 anyway); 1 M rows in Arrow is a manageable size, the earlier 10 M figure was not | Larger exports are an open option (a streaming `COPY TO` from a separate helper process) |
| D-024 | 2026-11-04 | Query timeout by `interrupt()` from a watcher thread, default 60 s | Verified: `interrupt()` from another thread raises `InterruptException` in the running query and leaves the connection usable; no signals, so it works the same on Windows and Linux | Every query, preview and summary runs under the timeout; a cancel button is an open option |
